## 为什么

应用需要支持大文件上传，通过接收来自前端的文件分片，按照分片索引排序，并通过文件流重构原始文件。这可以高效处理大文件，而不会耗尽服务器内存。

## 变更内容

- 添加新的API端点用于接收来自前端的文件分片
- 实现基于分片索引的排序逻辑
- 添加文件流功能以按顺序写入分片
- 确保对缺失或乱序分片的错误处理

## 功能

### 新功能

- `file-chunk-upload`: API端点，用于接收和处理文件分片，支持基于索引的排序和流式文件写入

### 修改的功能

无

## 影响

- 新增分片上传端点的API路由
- 用于流式写入的文件系统操作
- 可能需要用于分片缓冲的临时存储

## 详细设计

### 架构设计
采用MVC分层架构，将应用分为以下层次：

```
app/
├── api/                    # API层 - 路由控制器
│   ├── deps.py            # 依赖注入
│   └── v1/
│       └── endpoints/
│           └── file.py    # 文件上传相关端点
│
├── core/                   # 核心配置
│   ├── config.py          # 配置常量
│   └── exceptions.py       # 自定义异常
│
├── models/                 # 模型层
│   ├── orm.py             # ORM模型（预留）
│   ├── factory.py         # 数据库操作工厂（预留）
│   └── schema.py          # Pydantic请求/响应模型
│
├── services/               # 服务层
│   └── file_service.py     # 文件处理业务逻辑
│
└── utils/                  # 工具层
    ├── path_utils.py       # 路径处理
    └── file_utils.py       # 文件操作工具
```

### 各层职责
- **API层**: 路由定义、请求验证、调用Service、响应转换
- **Service层**: 业务逻辑文件处理
- **Models层**:
  - `orm.py`: 数据库ORM模型（预留）
  - `factory.py`: 数据库操作工厂（预留）
  - `schema.py`: Pydantic请求/响应模型
- **Utils层**: 通用工具函数
- **Core层**: 配置和异常定义

### 文件处理逻辑
1. web后端采用fastapi
2. 从前端接收文件分片，暂存到项目中的temp目录下，每一个需要上传的大文件都在temp目录下创建一个该文件的临时文件夹，该文件的分片都写在这个临时文件夹里面
3. 前端发送合并请求的时候，后端确认文件分块全部接收完毕，然后进行文件拼接
4. 拼接文件的方法：读取临时文件夹，按分片索引排序。利用文件流创建目标文件的可写流。依次将文件分片通过管道写入目标文件。目标文件一律放在项目的files目录下
5. 完成以后删除temp目录下的临时文件

- 接口设计
1. 前端上传文件分片到后端的接口 POST /api/file/chunk, 请求参数使用表单类型
2. 合并文件的接口 POST /api/file/merge
   - 请求参数（JSON）：
     {
       "fileName": "文件名",
       "totalChunks": "总分片数"
     }
   - 响应（JSON）：
     {
       "code": 200,
       "message": "文件合并成功",
       "data": {
         "fileUrl": "/uploads/文件名",
         "fileSize": 文件大小（字节）
       }
     }
